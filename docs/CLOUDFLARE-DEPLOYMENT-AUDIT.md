## Why saved content can remain absent

Tina's Save commits source to GitHub. The public static site changes only after a matching Cloudflare build successfully publishes it. The initial inventory's newest successful record is commit `4c0d1d6`, deployment `a6a05243-a716-4428-9c85-ae53135b47bc`, while newer source commits include failed or skipped builds. The latest failed source `b32caea` has a real CMS validation failure: `tool/jpg-compressor.faq[6].q` is empty. A newer failed source must never be mistaken for the currently served successful deployment. Actual custom-domain bytes and rendered content are verified separately in the release evidence.

The source history confirms how the invalid row arose. Commit `42fc316` first inserted eight JPG FAQ rows, seven initially blank; later Tina saves filled the first six while the last two remained empty objects. This is recorded from individual committed JSON snapshots, separately from deployment logs. A single invalid published record blocks the complete static build, including later edits to unrelated tools. Each captured failure is still attributed to its own log and source snapshot; an empty historical log is not assigned this cause by analogy.

## Skips and frequent Tina saves

Cloudflare documents that a queued build is skipped when a newer build for the same project, branch and deployment target is queued. Frequent field-by-field saves can therefore create many history entries while publishing only a later valid snapshot. This explains an available platform mechanism; it does not prove the reason for every one of the 293 skipped rows. [Official 11 August 2026 queued-build policy](https://developers.cloudflare.com/changelog/post/2026-08-11-skip-superseded-builds/).

Commit-message skip flags are also supported. A docs-only skip leaves the earlier verified application release live; it is not a failed application build. [Official GitHub build integration](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/).
